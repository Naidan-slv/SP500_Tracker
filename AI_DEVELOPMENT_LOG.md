### Entry 002 — Database Setup, Schema Migration, and Historical Data Ingestion
**Date:** 11 March 2026  
**Commit(s):** DB foundation and ingestion phase (commit batching in progress)

#### What Was Done
- Created environment/config/database connection foundation using `.env`, `app/config.py`, and `app/database/connection.py`
- Connected to Supabase PostgreSQL successfully after diagnosing hostname/network issues
- Added data exploration and cleansing pipeline scripts for the Kaggle dataset (`scripts/preview_kaggle_dataset.py`, `scripts/clean_kaggle_dataset.py`)
- Generated cleaned dataset output at `data/processed/top_companies_20y_daily_clean.csv`
- Implemented SQLAlchemy schema (`app/database/base.py`, `app/database/models.py`) for `stocks`, `stock_prices`, `users`, `portfolios`, `portfolio_holdings`, `watchlists`, and `watchlist_items`
- Initialized Alembic and autogenerated initial migration (`alembic/versions/ca28916cec49_initial_tables.py`)
- Applied migration to Supabase and verified all expected tables exist in `public` schema
- Implemented ingestion script `scripts/ingest_stock_prices.py` with chunked upsert logic
- Loaded cleaned historical OHLCV data into PostgreSQL

#### What I Asked the AI
- How to manage relational schema in a code-first way (instead of creating tables manually in Supabase)
- How to fix Supabase connection failures while keeping `.env`-based configuration
- How to safely clean and validate the Kaggle dataset before database insertion
- How to build an idempotent ingestion pipeline that can be rerun without duplicate data
- What commit strategy/message ordering should be used for clean project history

#### What the AI Produced
- Step-by-step guidance for SQLAlchemy + Alembic workflow
- A fix for the Supabase access issue by using the session pooler host and URL-safe credentials
- Validation/cleansing pipeline that standardises columns, parses dates, normalises tickers, coerces numeric fields, removes duplicate `(ticker, date)` records, and outputs a clean CSV
- Alembic configuration wired to project settings and migration autogeneration support
- Initial relational model set and migration script for all core entities
- Ingestion script using PostgreSQL `ON CONFLICT DO UPDATE` for both ticker-level and daily price-level upserts
- Progress checks and verification queries for row counts and date ranges

#### My Decisions and Overrides
- Preferred a code-first database workflow (SQLAlchemy + Alembic) instead of dashboard-first schema editing
- Kept development incremental after explicitly requesting slower, step-by-step execution
- Accepted recommendation not to treat Supabase dashboard as primary schema authoring tool
- Continued with historical data-first implementation to unlock later analytics/watchlist endpoints

#### Reflections
This session moved the project from planning into a functional backend data layer. The AI support was most useful for sequencing tasks correctly (connectivity, cleansing, schema, migration, ingestion) and for diagnosing practical issues (Supabase networking and module import path during script execution). I still made the key architectural decisions (code-first migrations, phased implementation, and commit hygiene), while using AI as an accelerator for implementation and troubleshooting.
